The Addys outbound journey.

One waterfall. Five tiers. 340,000 accounts routed on a single observable signal — and an invite code doing the work a demo request can't.

Core insight: Every competitor sells better memory. Addys sells the thing that happens after the memory. So we don't segment by title or industry — we segment by how close a prospect already is to the post-meeting execution problem, measured by what they've publicly already done about it. A G2 reviewer of Granola has already conceded the pain and paid to half-solve it. That's a different conversation than a cold pitch, and it's detectable with a scrape.

02

The routing spec

First match wins. A Granola reviewer who's also hiring a Chief of Staff routes to Tier 1 only — the stronger signal takes them, and they're never double-sent.

first match wins 
1. IF mac_forward_score = 0, OR headcount 500+, OR a competing notetaker/meeting-agent vendor, OR a GTM/outbound agency -> SUPPRESS (Mac-only is a hard disqualifier today, and we'd rather lose the lead at list-build than collect 'we're a Windows shop' replies that pollute the tier reads.)
2. IF notetaker_tool != none-detected -> TIER 1 - Committed Notetaker (Proven budget, proven adjacent pain, named individual, zero education required. They solved capture and never solved execution.)
3. IF ELSE IF open_req_title != none AND req_posted_days_ago <= 45 -> TIER 2 - Hiring the Human Workaround (They wrote the job description for the problem. The req is the pain statement, in their own words, timestamped and public.)
4. IF ELSE IF booking_link_platform != none -> TIER 3 - Live on a Public Calendar (The calendar is the job. The admin tail behind each meeting scales linearly with it and is the first thing to slip on a heavy week.)
5. IF ELSE IF exec_stack contains 2 or more of [HubSpot, Notion, Linear, Slack] -> TIER 4 - The Stack Is Already Wired (Four systems that don't talk to each other at the moment a decision gets made. Multi-tool stacks don't reduce the retyping tax, they multiply it.)
6. IF ELSE -> TIER 5 - Catch-all (Everything remaining in the TAM. Broadest copy, softest ask, no lead left unrouted.)

Launch order and read thresholds

Tier 1 first for the cheapest read. Catch-all last, and only once invite fulfilment is proven — a flood of code requests you can't service is worse than no campaign.

launch first
01

Weeks -2 to 0 - Infrastructure. Domains, mailboxes, warmup, suppression lists, and calibration of the Mac-forward filter. Most importantly: the invite-code fulfilment SOP - who sends the code, how fast, from which inbox.

02

Weeks 1-3 - Tier 1 only, 150-250/day. The cheapest and fastest read in the waterfall. Validate the wedge before spending any TAM on the weaker tiers.

03

Weeks 4-6 - Add Tier 2, 400-600/day. Introduce the timing-driven tier and compare it against the Tier 1 baseline.

04

Weeks 7-10 - Add Tier 3, 800-1,200/day. The largest tier that still supports a genuinely personal opener.

05

Weeks 11+ - Full waterfall, 1,500-2,500/day. Tiers 4 and 5 come last, and only once the fulfilment loop is proven end to end.

06

Throughout - fulfilment is the real bottleneck, not sending. A cold email promising an invite code creates an obligation with a shelf life of about two hours. Cap daily volume at whatever can actually be serviced same-day, and grow from there.

Scale / cut rules

1 positive reply per 150 contacted Perfect. Scale this tier hard.
1 per 300 Good. Let it run untouched.
1 per 450-500 Borderline. Test one copy variant and hold everything else constant.
Worse than 1 per 500, or under 1% reply rate after 1,500+ sends Cut the tier and rework the trigger.
Code request rate, code-to-download rate, download-to-connected-app rate Track alongside reply rate. Reply rate is a vanity number here if the codes never get redeemed.
Mac disqualification rate above 5% of replies The Mac-forward filter is too loose. Tighten it before it distorts the tier reads.
